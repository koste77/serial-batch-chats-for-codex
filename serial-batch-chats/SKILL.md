# 串行多会话任务调度

把已获授权的完整任务拆为有输入、输出和验收条件的批次。主会话制定计划、创建聊天、等待、核对记录；执行聊天负责本批实现、试验、评审、修复及归档。持续推进到全部通过、用户规定的暂停点或真实阻塞。

## 制定可执行计划

1. 确认项目根、现有规则及正在运行的调度器；已有运行先接管监控，避免重复启动。保留用户及其他会话的改动。
2. 将计划和交接放进一个独立运行目录，例如 `.batch-runs/<任务名>/`。按依赖排序为 B01、B02 等，每批限定范围，写明前批输入、交付文件、可核验的验收项、所需评审、失败交接及可选暂停点。批次数量由任务决定。
3. 为每批准备单独提示文件，指定计划路径、当前批次、可写范围、输入摘要核验、证据格式和完成信号。只从项目文件接手，不依赖主会话未落盘的上下文。
4. 明确会话标题为计划中的批次标题全文加 `｜<任务名>`。将计划、提示文件的摘要和调度状态落盘；不要引入用户未要求的 Git 提交、推送或远程发布。

具体文件协议与提示模板见 [references/protocol.md](references/protocol.md)。双 reviewer、验收项数量和 B01 后暂停都由项目规则或用户要求决定，不把某个工程的要求强加给所有任务。

## 创建真正的项目聊天

先发现 `create_thread`、`wait_threads`、`read_thread` 等产品工具。用户明确授权创建多聊天后，才能创建这些用户可见聊天。内部评审用 subagent；它们不代替用户要求的批次聊天。

有原生工具时按其实际 schema 指定相同项目和工作目录，并记录返回的真实 thread ID。没有原生工具时，阅读 [references/desktop-fallback.md](references/desktop-fallback.md)，可使用本 skill 的 `scripts/desktop_batches.py`。此备用实现依赖本机实验性 App Server，字段不匹配就停止，不能回退为后台 `codex exec`。

创建后回读项目归属、完整标题、持久化状态以及项目聊天列表。首条输入只发送一次。不要以普通子进程的 session ID 冒充聊天 ID。Windows 备用通道还须调用已打包的 `refresh_desktop_project.ps1` 折叠/展开目标项目，以可访问性控件确认标题；只查后台列表可能留下尚未刷新的侧栏。不要截图或读取桌面画面。项目归属或侧栏刷新失败时保留已创建聊天，停止后续派发，不通过重复创建修复显示。

## 串行监控和放行

- 主会话只关注执行状态及落盘验收；工程判断留给执行者和计划要求的 reviewer。
- 优先用 `wait_threads` 的单目标有界等待与 cursor。无变化时不重复叙述；出现完成、失败、需用户介入或实质进展时更新。一次等待不超过 60 秒，不用定时自动化代替当前任务的跟进。
- 只有当前 turn 正常完成、所有验收项有真实证据且通过、所需 reviewer 均返回并处置、交接文件存在，才记录 PASS 并创建下一聊天。正常结束不等于验收通过；缺文件、哈希变化、BLOCKED 或缺审都不能放行。
- 使用单调度锁、每批 thread/turn ID、创建前意图和创建后回执防止重复派发。恢复时回读原会话并接着等待，不因网络断开或主会话重启而自动重建、重发。创建请求结果不明时先核对服务端与项目列表，保留不确定状态。
- 执行聊天可修复的问题交回同一聊天；原聊天仍在运行时不重复发送“继续”。真实阻塞记录原因、已尝试步骤和恢复条件，暂停后续批次。用户规定的暂停点保持 PAUSED，收到继续指令后才放行。

## 收尾与自检

逐批报告标题、聊天 ID、验收结果和证据目录，再给最终交付文件及索引。使用原生 `create_thread` 成功创建聊天时，按宿主要求输出 `::created-thread`；备用协议创建应报告实际 ID，不伪称原生工具结果。

需要验证安装和流程时使用 [references/smoke-test.md](references/smoke-test.md)：两个顺序创建的简单聊天，第二批从第一批文件接手。先跑本地门禁测试，再做真实聊天测试；分开报告静态校验、离线测试与真实聊天结果。
